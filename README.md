# starpets-qa

Test automation framework for StarPets — QA Engineer assessment.

Stack: Python 3.11 · Playwright · pytest · requests · pydantic

---

## Project Structure

```
starpets-qa/
├── config/
│   └── settings.py                   # pydantic-settings, reads from .env
├── api/
│   └── api_posts/
│       ├── models/
│       │   └── post.py               # Pydantic v2 model: PostModel
│       └── posts_client.py           # requests.Session wrapper, no assertions
├── pages/
│   └── catalog_page/
│       ├── catalog_page.py           # Playwright Page Object for StarPets catalog
│       └── catalog_page_locators.py  # локаторы отдельно от логики страницы
├── tests/
│   ├── conftest.py                   # fixtures: api_client, browser_instance, page, catalog_page
│   ├── api/
│   │   ├── test_get_posts.py         # 2 API tests: get by id (positive, 404)
│   │   └── test_create_posts.py      # 5 API tests: create (positive, negative, auth, idempotency)
│   └── ui/
│       └── test_catalog.py           # 1 E2E UI test: buy → WS confirmation → withdraw
├── Dockerfile                        # python:3.11-slim + Playwright Chromium
├── docker-compose.yml                # services: tests, tests-api-only, tests-ui-only
├── Makefile                          # shortcuts for local and Docker runs
├── pytest.ini                        # markers, HTML report config
├── requirements.txt                  # pinned versions
└── .env.example                      # environment variables template
```

## Quick Start — Local (recommended)

```bash
# Prerequisites: Python 3.11+

git clone https://github.com/Wiva-Cox/starpets-qa
cd starpets-qa

python -m venv .venv
source .venv/bin/activate      # Windows: .venv\Scripts\activate

pip install -r requirements.txt
playwright install chromium

cp .env.example .env

# Run all tests
pytest

# API only
pytest -m api

# UI only
pytest -m ui

# UI with visible browser
make test-headed
```

## Architecture Decisions

**requests вместо httpx для API-слоя** — синхронные тесты не требуют async I/O, а requests — широко известный стандарт. httpx добавляет сложность без реальной пользы в данном контексте.

**Pydantic для валидации ответов** — парсинг ответов через `PostModel(**response.json())` работает как живой контракт схемы. Переименование поля или смена типа на бэкенде сразу роняет тест с понятным `ValidationError`, а не с загадочным `KeyError` внутри ассертов.

**Page Object pattern** — локаторы живут в `CatalogPage`, а не в тестах. Локаторы вынесены отдельно в `catalog_page_locators.py`, чтобы при смене селектора правка была в одном месте. Тесты читаются как описание поведения.

**data-testid как приоритет локаторов** — CSS-классы и текст кнопок — это детали дизайна, которые меняются при каждом редизайне. `data-testid` — это контракт между QA и разработчиками. На реальном проекте StarPets мы бы заранее согласовали с фронтенд-командой добавление этих атрибутов на все интерактивные элементы.

**WebSocket без sleep()** — `page.expect_websocket()` перехватывает реальное WS-соединение при загрузке страницы. `ws.wait_for_event("framereceived", predicate=..., timeout=60_000)` poll'ит очередь событий до получения нужного фрейма с подтверждением оплаты. Хардкодных задержек нет.

### 1. Критика требований и вопросы к PM

#### Противоречие: внутренний баланс vs. редирект на внешнюю платёжку

**Фрагмент из описания PM:**
> "Бэкенд рассчитывает курс и отправляет запрос в платёжный шлюз. Юзер редиректится на внешнюю платёжку."

**Фрагмент из технического контекста:**
> "У юзера есть баланс на аккаунте — пополнил один раз и покупает предметы в один клик."

**Проблема:** В документе описаны два взаимоисключающих флоу оплаты. Если у пользователя есть внутренний баланс — редирект на внешний шлюз не нужен. Если происходит редирект — баланс не участвует. Непонятно, когда используется какой сценарий, и являются ли они двумя разными точками входа или одним флоу.

**Вопрос PM:** Это один флоу или два параллельных сценария покупки? Если два — где граница между ними и как пользователь выбирает способ оплаты?

---

#### "Один клик" — не измеримо и не соответствует описанному флоу

**Фрагмент:**
> "Покупка и вывод внутриигрового предмета в один клик"

**Проблема:** "Один клик" не является измеримым критерием. По тому же документу пользователь совершает минимум 6 действий: нажимает кнопку на сайте → проходит внешнюю платёжку → заходит в Roblox → добавляет бота в друзья → заходит на приватный сервер → принимает трейд. Тест невозможно написать против неизмеримого требования.

**Вопрос PM:** "Один клик" — это маркетинговое название фичи или буквальное функциональное требование? Если требование — какие шаги входят в его периметр, а какие считаются действиями пользователя вне нашей ответственности?

---

#### "Бэкенд рассчитывает курс" — не указан момент фиксации

**Фрагмент:**
> "Бэкенд рассчитывает курс и отправляет запрос в платёжный шлюз"

**Проблема:** Курс валют меняется постоянно. Неясно, в какой момент он фиксируется: в момент нажатия кнопки, в момент перехода на платёжку, или в момент фактического списания. Без этой информации невозможно написать тест, проверяющий корректность суммы к оплате.

**Вопрос PM:** На какой момент фиксируется курс? Есть ли TTL на рассчитанную цену (например, "цена действительна N минут")? Кто несёт курсовую разницу, если пользователь открыл платёжку, но оплатил через 20 минут?

---

#### "Оплачивает в своей валюте + комиссия" — неопределённая природа комиссии

**Фрагмент:**
> "Юзер оплачивает в своей валюте (например, BRL) + комиссия"

**Проблема:** Не определено, что такое "комиссия" — комиссия платёжного шлюза, наценка сайта за конвертацию, или комиссия за транзакцию. Неизвестно, кто её платит (пользователь сверху цены или она включена), как она рассчитывается и отображается ли она пользователю до подтверждения оплаты. Слово "например, BRL" оставляет неясным список поддерживаемых валют.

**Вопрос PM:** Что именно называется "комиссией", как она рассчитывается и отображается пользователю? Какие валюты поддерживаются?

---

#### Кто выполняет конвертацию EUR → локальная валюта?

**Фрагмент:**
> "Бэкенд рассчитывает курс и отправляет запрос в платёжный шлюз (в валюте EUR). Юзер оплачивает в своей валюте."

**Проблема:** Неясно, кто делает конвертацию — наш бэкенд передаёт сумму в EUR, а платёжный шлюз конвертирует на своей стороне? Или бэкенд сам считает итоговую сумму в BRL и передаёт её в шлюз? Это определяет, чей курс и чья логика округления используются, что напрямую влияет на тесты расчёта суммы.

**Вопрос PM:** Конвертацию EUR → локальная валюта делает наш бэкенд или платёжный шлюз?

---

#### "Платёжка возвращает успешный вебхук" — описан только happy path

**Фрагмент:**
> "Платёжка возвращает успешный вебхук, система шлёт событие в RabbitMQ"

**Проблема:** В документе описан исключительно сценарий успешной оплаты. Не описано ни одного альтернативного флоу: отказ оплаты, отмена пользователем, недоставленный вебхук, дублирующийся вебхук. Без этого нельзя написать негативные тесты и нельзя определить ожидаемое поведение системы при сбое.

**Вопрос PM:** Где описание поведения системы при неуспешной оплате, отмене и недоставленном вебхуке?

---

#### Противоречие: "бот находит юзера" или "юзер сам заходит к боту"

**Фрагмент из описания PM:**
> "Бот находит юзера в игре, передаёт пета"

**Фрагмент из технического контекста:**
> "Юзер сам заходит на приватный сервер бота"

**Проблема:** Два абзаца одного документа описывают противоположную механику. "Бот находит юзера" и "юзер сам заходит к боту" — это принципиально разные флоу с разными сценариями ошибок и разными ожиданиями от пользователя.

**Вопрос PM:** Кто к кому приходит — бот ищет пользователя в игре, или пользователь сам заходит на сервер бота?

---

#### "Передаёт пета через Computer Vision" — некорректная формулировка

**Фрагмент:**
> "Бот находит юзера в игре, передаёт пета через Computer Vision"

**Проблема:** Computer Vision — это инструмент распознавания изображений, а не механизм передачи предметов. Пета передаёт бот через встроенную механику трейда в Roblox. CV только фиксирует факт передачи. Формулировка смешивает инструмент и действие, что создаёт неоднозначность при написании тестов.

**Вопрос PM:** Уточни формулировку: бот передаёт пета через трейд в Roblox, а CV подтверждает факт передачи — так? Или CV участвует в самой механике трейда?

---

#### "Статус на сайте → Success" — не указан триггер

**Фрагмент:**
> "Статус на сайте → «Success»"

**Проблема:** Не указано, какое именно событие переводит заказ в статус Success: подтверждение от CV, подтверждение от бота, подтверждение от Roblox, или факт принятия трейда пользователем. Каждый вариант имеет разную надёжность и разные условия ложного срабатывания.

**Вопрос PM:** Статус Success выставляется по какому событию — и кто является источником этого события?

---

#### Не описано, как пользователь узнаёт имя бота

**Фрагмент:**
> "Юзер отправляет боту заявку в друзья → бот принимает"

**Проблема:** Не описан момент и способ передачи пользователю имени бота. До оплаты? После? Через сайт, email, личный кабинет? Пользователь уже заплатил, и если он не знает имя бота или не получил уведомление — процесс встал без очевидного следующего шага.

**Вопрос PM:** В какой момент и через какой канал пользователь получает имя бота, которому нужно отправить заявку в друзья?

---

#### "Авторизованный юзер" — авторизован где?

**Фрагмент:**
> "Авторизованный юзер нажимает «Купить и вывести»"

**Проблема:** Неясно, что включает в себя "авторизованный" в данном контексте — авторизован на сайте StarPets, в Roblox, или в обоих местах одновременно. Для доставки пета боту необходим Roblox-аккаунт. Документ не говорит, является ли привязка Roblox-аккаунта обязательным условием для кнопки "Купить и вывести".

**Вопрос PM:** Является ли привязка Roblox-аккаунта обязательным условием для совершения покупки? Если аккаунт не привязан — кнопка заблокирована, или ошибка возникает уже после оплаты?

### 2. Граничные сценарии (Edge Cases)

Ниже перечислены критичные сценарии, которые могут заблокировать вывод предмета, сломать баланс пользователя или привести к потере пета

#### Оплата и баланс

- Оплата прошла на стороне шлюза, но вебхук не дошёл до нашего сервера → деньги списаны, заказ не создан
- Пользователь нажал кнопку дважды быстро → два заказа, двойное списание за один пет
- Курс EUR/BRL изменился между расчётом цены и моментом фактической оплаты → пользователь заплатил больше или меньше отображённой суммы
- Внутренний баланс списан, но запрос к платёжному шлюзу упал → баланс уменьшен, заказ не создан
- Вебхук от платёжки пришёл дважды (retry на стороне шлюза) → возможна двойная активация доставки

#### Очередь RabbitMQ

- Сообщение отправлено в очередь, но consumer его потерял (нет dead letter queue) → задача исчезла без следа
- Consumer обработал задачу дважды (at-least-once delivery) → бот пытается отдать пета дважды
- Очередь переполнена при пиковой нагрузке → задержка доставки на неопределённое время без уведомления пользователя

#### Бот в Roblox

- Бот офлайн или упал в середине трейда → трейд не завершён, статус на сайте завис
- Roblox-сервер упал в момент трейда → трейд отменён, но сайт не получил уведомления
- Несколько пользователей зашли на сервер бота одновременно → бот торгует не с тем пользователем
- Пользователь отклонил трейд → повторная попытка или возврат средств? Не описано
- Пользователь не зашёл в игру за N времени → задача висит в очереди бесконечно

#### Computer Vision

- Ложно-положительное срабатывание: CV решила, что трейд прошёл, а пет не передан → статус Success, пользователь ничего не получил
- Ложно-отрицательное срабатывание: трейд прошёл, но CV не зафиксировала → статус завис в processing
- Лаги в игре или низкий FPS → CV не успела обработать кадр с подтверждением трейда

####  Пользователь и аккаунт

- Roblox-аккаунт пользователя заблокирован → бот не может найти пользователя в игре
- Пользователь сменил никнейм в Roblox между оформлением заказа и получением пета → бот ищет несуществующего пользователя
- Пользователь не добавил бота в друзья → доставка невозможна, деньги уже списаны, нет описания дальнейшего флоу

### 3. Пострелизный мониторинг

Доступа к БД нет. Наблюдаем снаружи через логи, метрики и внешние инструменты.

#### Метрики для наблюдения в первый час после релиза

- **Конверсия воронки по шагам:** клик "Купить и вывести" → платёж создан → вебхук получен → задача в очереди → статус Success. Падение на любом шаге указывает на место сбоя.
- **Время от оплаты до статуса Success** — медиана и p95. Рост этого показателя говорит о затруднении где-то в цепочке доставки.
- **Доля заказов в статусе "processing" дольше N минут** — индикатор зависших задач.
- **Глубина очереди RabbitMQ** — если растёт и не падает, consumer не справляется.
- **Количество обращений в поддержку с темой "заплатил, пета нет"** — самый прямой пользовательский сигнал.

#### Паттерны ошибок

- Всплеск 4xx/5xx на вебхук-эндпоинте → платёжный шлюз не может уведомить нашу систему
- Ошибки таймаута или connection refused на RabbitMQ consumer → очередь не обрабатывается
- Рост dead letter queue → задачи падают и не переотправляются
- Повторяющиеся ошибки с одинаковым order_id → дубли обработки

#### Инструменты

- **Sentry / Datadog** — ошибки в реальном времени, алерты по порогам
- **Grafana + RabbitMQ Management UI** — глубина очереди, consumer lag, количество nack
- **Kibana или любой лог-агрегатор** — поиск по error-паттернам, фильтрация по статусам заказов
- **Statuspage платёжного шлюза** — убедиться, что проблема не на стороне партнёра
- **Внутренний мониторинг бота** — количество успешных и неуспешных трейдов, время жизни сессии в игре
